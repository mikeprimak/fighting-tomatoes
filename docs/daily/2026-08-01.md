# 2026-08-01 — Vercel invocation-spike alert: an unattributed scraper walking the fight catalog

Vercel sent a medium-severity anomaly alert on `packages/web`:
**"Function Invocations spike with external API failures"**, 19× above the
7-day average, starting **Jul 29 15:00 UTC** — 186 invocations per 5 min
baseline against 3.5k per 5 min at the time of the mail.

## 1. What the traffic actually was

Runtime logs for the 6 hours before the investigation: **9,765 function
invocations** (plus 9,168 CDN hits) across **5,942 distinct URLs**. Grouped by
route:

| route | invocations / 6h |
|---|---|
| `/fighters/[id]` | 3,751 |
| `/fights/[id]` | 2,065 |
| `/events/[id]` | 1,381 |
| `/fights/best/[list]` | 586 |
| `/download` | 506 |
| `/fights/[id]/opengraph-image` | 472 |
| `/fighters` | 409 |
| `/api/auth/refresh` | 276 |

Every catalog hit was `cache=MISS`. The shape — near-uniform counts across the
whole programmatic-SEO corpus, one section at a time — is a bulk crawl, not
users.

The alert's "external API failures" half was the same event seen from the other
side: **209 `TypeError: fetch failed`** against
`fightcrewapp-backend.onrender.com` (`ECONNRESET`, `write ETIMEDOUT`,
`UND_ERR_SOCKET: other side closed`). The crawl was pushing the 256 MB Render
instance past what it could answer, so some SSR renders came back without data.

## 2. Identifying the crawler: Vercel runtime logs carry no user agent

This is the part worth remembering. Vercel's runtime log lines have
`requestPath`, `responseStatusCode`, `cache`, `source`, `deploymentId` — and
**no user agent, and no client IP**. `vercel logs --json` doesn't add them
either. The `Block bulk crawlers` firewall rule (21 named bots, added during the
July free-tier blowout) was live and clearly not catching this one, but there was
no way to see who it was from the logs.

The technique that worked: **`console.log` the UA from inside a route that is
already dynamically rendered**, so the probe costs nothing. `/fighters/[id]` and
`/fights/[id]` re-render on every request anyway, so
`console.log('[ua-probe]', (await headers()).get('user-agent'))` added zero
invocations and no latency, and the value shows up under the request in the
runtime logs.

Trap hit on the first attempt: the crawler works **one section at a time**. The
probe went on `/fighters/[id]` (highest volume over 6h), and by the time it
deployed the crawler had moved to `/fights/[id]` — 497 invocations in 10 min
there against 20 on the probed route. Both routes needed the probe.

## 3. The culprit

```
Mozilla/5.0 (research; contact you@example.com)
```

Someone running a scraper with the **placeholder user agent from a tutorial or
library example**, never filled in. ~85-90% of all log lines, roughly one
request per second, ignoring robots.txt.

It was walking the fight catalog in **both slug orderings** —
`dean-lister-vs-yuki-sasaki` *and* `yuki-sasaki-vs-dean-lister`,
`josh-koscheck-vs-jonathan-goulet` *and* `jonathan-goulet-vs-josh-koscheck` —
which is why the distinct-URL count was so high. Worth noting for its own sake:
both orderings resolve and render, i.e. the fight catalog serves ~2× the URLs it
needs to. (Related to `lesson_tapology_rename_forks_fight_dup`'s order-sensitive
Fight unique constraint, but this is the web routing layer, not the DB.)

## 4. Fix shipped

**Firewall rule `Block placeholder-UA scraper`** (added + published to
production via `vercel firewall rules add … && vercel firewall publish`):

```
user agent contains "(research; contact"  →  Deny
```

Verified live:

| request | result |
|---|---|
| `-A "Mozilla/5.0 (research; contact you@example.com)"` | **403** |
| `-A "…Chrome/142.0.0.0 Safari/537.36"` | 200 |
| `-A "…Googlebot/2.1…"` | 200 |

Last log line from that UA: 16:30:58 UTC, seconds before the rule published.
Nothing since.

**ISR on `/fights/best/[list]`** (`export const revalidate = 3600`). That route
burned 586 invocations in 6h re-rendering HTML while every `fetchBest*` call
inside it was already cached for an hour — page-level ISR was simply missing.
3600 matches the `lib/bestFights.ts` fetch defaults, so freshness is unchanged.

The two UA probes were removed once the answer was in hand.

## 5. Still open — a second, UA-rotating scraper

Removing the loud one exposed a quieter one that rotates fake user agents:

- `Chrome/150.0.0.0` on Linux — **Chrome 150 does not exist** (142 is current)
- `Chrome/107.0.0.0` on Windows, `Chrome/109.0.0.0` on Mac
- `Chrome/55.0.1869.1661` on Android 5.0 — malformed version string
- `ShapBot/0.1.0`

Tell: the *same* URL fetched by two different "browsers" seconds apart —
`/fighters/gilbert-urbina` by "Chrome/150 Linux" at 16:32:42 and "Chrome/107
Win" at 16:32:34, each preceded by the same UUID→slug 308. It was running
~20 requests/min on `/fights/[id]` after the block.

UA-based blocking doesn't work on a rotating pool. The tool that does is a WAF
**rate limit keyed on `ip` or `ja4`** (`vercel firewall rules add … --action
rate_limit --rate-limit-keys ja4 --rate-limit-requests N --rate-limit-window
60`). **Not shipped, deliberately** — a naive IP rate limit would also throttle
Googlebot during a crawl burst, and throttling Googlebot would damage the
primary growth workstream (`operation-own-the-serps`). Any rule here needs to
exclude verified search engines first, or start at `--action log` to size the
threshold against real crawl rates. Mike's call.

## 6. Not done (recommended, sized)

- **ISR the catalog routes** (`/fighters/[id]`, `/fights/[id]`, `/events/[id]`).
  Their fetches are cached (60-300s) but the *pages* re-render every request.
  `export const revalidate = 60` would match existing freshness exactly and cost
  nothing in staleness. Deliberately not shipped today: during a backend outage
  ISR would cache the degraded no-data render for the TTL, where today each
  request retries. Worth doing, worth doing with eyes open — the 60s TTL keeps
  the blast radius small.
- The double-ordering fight URLs (§3) are ~2× the catalog Google has to crawl.
  Canonicals presumably already collapse them; worth confirming against the
  sitemap.
