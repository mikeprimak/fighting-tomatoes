# 2026-08-01 — Vercel invocation-spike alert: an unattributed scraper walking the fight catalog

Vercel sent a medium-severity anomaly alert on `packages/web`:
**"Function Invocations spike with external API failures"**, 19× above the
7-day average, starting **Jul 29 15:00 UTC** — 186 invocations per 5 min
baseline against 3.5k per 5 min at the time of the mail.

## 1. What the traffic actually was

Runtime logs for the 6 hours before the investigation: **9,765 function
invocations** (plus 9,168 CDN hits) across **5,942 distinct URLs**. Grouped by
route:

| route | invocations / 6h |
|---|---|
| `/fighters/[id]` | 3,751 |
| `/fights/[id]` | 2,065 |
| `/events/[id]` | 1,381 |
| `/fights/best/[list]` | 586 |
| `/download` | 506 |
| `/fights/[id]/opengraph-image` | 472 |
| `/fighters` | 409 |
| `/api/auth/refresh` | 276 |

Every catalog hit was `cache=MISS`. The shape — near-uniform counts across the
whole programmatic-SEO corpus, one section at a time — is a bulk crawl, not
users.

The alert's "external API failures" half was the same event seen from the other
side: **209 `TypeError: fetch failed`** against
`fightcrewapp-backend.onrender.com` (`ECONNRESET`, `write ETIMEDOUT`,
`UND_ERR_SOCKET: other side closed`). The crawl was pushing the 256 MB Render
instance past what it could answer, so some SSR renders came back without data.

## 2. Identifying the crawler: Vercel runtime logs carry no user agent

This is the part worth remembering. Vercel's runtime log lines have
`requestPath`, `responseStatusCode`, `cache`, `source`, `deploymentId` — and
**no user agent, and no client IP**. `vercel logs --json` doesn't add them
either. The `Block bulk crawlers` firewall rule (21 named bots, added during the
July free-tier blowout) was live and clearly not catching this one, but there was
no way to see who it was from the logs.

The technique that worked: **`console.log` the UA from inside a route that is
already dynamically rendered**, so the probe costs nothing. `/fighters/[id]` and
`/fights/[id]` re-render on every request anyway, so
`console.log('[ua-probe]', (await headers()).get('user-agent'))` added zero
invocations and no latency, and the value shows up under the request in the
runtime logs.

Trap hit on the first attempt: the crawler works **one section at a time**. The
probe went on `/fighters/[id]` (highest volume over 6h), and by the time it
deployed the crawler had moved to `/fights/[id]` — 497 invocations in 10 min
there against 20 on the probed route. Both routes needed the probe.

## 3. The culprit

```
Mozilla/5.0 (research; contact you@example.com)
```

Someone running a scraper with the **placeholder user agent from a tutorial or
library example**, never filled in. ~85-90% of all log lines, roughly one
request per second, ignoring robots.txt.

It was walking the fight catalog in **both slug orderings** —
`dean-lister-vs-yuki-sasaki` *and* `yuki-sasaki-vs-dean-lister`,
`josh-koscheck-vs-jonathan-goulet` *and* `jonathan-goulet-vs-josh-koscheck` —
which is why the distinct-URL count was so high. Worth noting for its own sake:
both orderings resolve and render, i.e. the fight catalog serves ~2× the URLs it
needs to. (Related to `lesson_tapology_rename_forks_fight_dup`'s order-sensitive
Fight unique constraint, but this is the web routing layer, not the DB.)

## 4. Fix shipped

**Firewall rule `Block placeholder-UA scraper`** (added + published to
production via `vercel firewall rules add … && vercel firewall publish`):

```
user agent contains "(research; contact"  →  Deny
```

Verified live:

| request | result |
|---|---|
| `-A "Mozilla/5.0 (research; contact you@example.com)"` | **403** |
| `-A "…Chrome/142.0.0.0 Safari/537.36"` | 200 |
| `-A "…Googlebot/2.1…"` | 200 |

Last log line from that UA: 16:30:58 UTC, seconds before the rule published.
Nothing since.

The two UA probes were removed once the answer was in hand.

## 4b. ISR on the catalog routes — and the export that actually turns it on

`/fights/[id]`, `/fighters/[id]`, `/events/[id]` and `/fights/best/[list]` were
**7,197 of the 9,765 invocations** (74%). Every one was a `cache=MISS`: the
`fetch` calls inside each route were cached (60-300s), but the *rendered HTML*
was not, so each request re-rendered from scratch **and re-hit the Render
backend** — which is exactly what produced the `fetch failed` storm in §1.

Adding `export const revalidate = N` did nothing. Deployed, and
goodfights.app still answered:

```
Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate
X-Vercel-Cache: MISS      # on every repeat request
```

The tell was in the comparison: `/schedule` (no dynamic segment) and
`/orgs/[org]` (dynamic segment **with** `generateStaticParams`) were caching
fine; the catalog routes, all dynamic segments **without** one, were not. The
bundled Next 16 docs say it outright —
`next/dist/docs/…/generate-static-params.md`:

> You must return **an empty array from `generateStaticParams`** or utilize
> `export const dynamic = 'force-static'` in order to revalidate (ISR) paths at
> runtime.

So the working pair on a dynamic segment is:

```ts
export const revalidate = 60;
export function generateStaticParams() {
  return [];
}
```

Empty array = prerender nothing at build (the catalog is ~5,900 URLs and the
backend may be cold), render each path on first request, then cache it.

Verified on all four routes after deploy — `Cache-Control: public`, and
**MISS → HIT** on the second request. Content and SEO intact: titles render,
`SportsEvent`/`Person` JSON-LD is present, and the UUID→slug 308
canonicalization still fires (`/events/2433d86f-…` → `/events/ufc-fight-night-medic-vs-rodriguez`).

60s matches the fetch revalidate already in each route, so nothing got staler.
Live data reaches the client through React Query on mount regardless of the
SSR snapshot's age.

## 4c. Rate-limit backstop

Rule **`Rate limit catalog crawls`**: 300 req / 60s keyed on **ip + ja4**
(TLS fingerprint), on `path matches ^/(fights|fighters|events)/` only — so
static assets and `/_next/*` never count toward it — with Googlebot, bingbot,
Applebot, DuckDuckBot, YandexBot, SeznamBot, OAI-SearchBot, ChatGPT-User,
Perplexity and Claude-User **explicitly exempted** so no search engine can ever
be throttled. Exceeding it denies for 1m.

Honest framing: at 300/min this does **not** catch the §5 rotating scraper,
which is deliberately polite at ~13-20 req/min. A threshold low enough to catch
it would endanger real users (Next.js prefetches `.rsc` for links in view, so a
human on `/fights/top` can fire a lot of catalog requests in a minute). It is a
**backstop against the next runaway** — the thing that would have capped
2026-07-29 at 300/min instead of letting it reach 3.5k/5min. The §4b ISR change
is what actually neutralises a polite crawler: its requests now hit the CDN.

## 5. Still open — a second, UA-rotating scraper

Removing the loud one exposed a quieter one that rotates fake user agents:

- `Chrome/150.0.0.0` on Linux — **Chrome 150 does not exist** (142 is current)
- `Chrome/107.0.0.0` on Windows, `Chrome/109.0.0.0` on Mac
- `Chrome/55.0.1869.1661` on Android 5.0 — malformed version string
- `ShapBot/0.1.0`

Tell: the *same* URL fetched by two different "browsers" seconds apart —
`/fighters/gilbert-urbina` by "Chrome/150 Linux" at 16:32:42 and "Chrome/107
Win" at 16:32:34, each preceded by the same UUID→slug 308. It was running
~20 requests/min on `/fights/[id]` after the block.

UA-based blocking can't catch a rotating pool, and the rate limit in §4c is set
too high to catch this one specifically. What neutralises it is the §4b ISR
change: its requests now hit the CDN instead of a function, so it costs
invocations only on the first fetch of each URL per 60s window. Left running
rather than blocked — it is not currently expensive, and any UA rule aimed at
generic Chrome strings risks real users.

## 6. Still open

- **A backend outage now caches a degraded render for up to 60s.** With ISR, if
  the Render fetch fails the no-data shell is what gets cached, where before
  every request retried. The 60s TTL keeps the blast radius small and
  stale-while-revalidate self-heals, but it is a real behaviour change worth
  knowing about the next time the backend wobbles.
- **Fight URLs resolve in both slug orderings** (§3) —
  `a-vs-b` and `b-vs-a` both render. That is ~2× the catalog Google has to
  crawl. Canonicals presumably collapse them; worth confirming against the
  sitemap and, if so, 308ing the non-canonical ordering the way UUIDs already
  are.
- `ShapBot/0.1.0` is not in `robots.ts` `BLOCKED_BOTS`. Low volume, harmless so
  far; add it if it grows.

## Reference

- Firewall rules live in **Vercel, not git** (same as
  `lesson_vercel_bot_overage_firewall_rule`). Three rules now: `Block bulk
  crawlers` (21 named bots), `Block placeholder-UA scraper`, and `Rate limit
  catalog crawls`.
- `vercel firewall rules list|inspect|add`, then `vercel firewall publish` —
  `add` only *stages* a draft.
- Valid condition operators (the CLI will tell you if you pass a bogus one):
  `eq, inc, sub, pre, suf, re`. `re` is a regex, which is how the rate limit
  scopes to `^/(fights|fighters|events)/` in a single condition — multiple
  `--condition` flags are AND'd, so path alternation can't be done with `--or`
  without repeating every negated-UA condition per group.
- Never trust the source for caching behaviour — read
  `X-Vercel-Cache` / `Cache-Control` off the live URL twice in a row.
