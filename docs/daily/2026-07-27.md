Two follow-ups from yesterday. One overturns a number we wrote down; the other

## 1. Was last night's proxy usage reasonable? Yes — but yesterday's model of it was wrong

Zuffa Boxing 9 ran to completion after the top-up. The tracker behaved: the
shared-browser fix held, and the night cost roughly what a card should cost.
But measuring it properly showed **the money is not going where yesterday's
audit said it was.**

### What last night actually cost

Journal window 23:17 Jul 26 (top-up lands) → 03:25 Jul 27 (card ends):

| | Count |
|---|---|
| Completed scrapes | 65 |
| …of those, needing a CapSolver solve | 27 |
| …reusing an existing clearance | 38 |
| Shared-browser recycles | 12 (7 idle, 4 no-tracker, 1 max-age) |
| Pre-top-up failed polls (`407 TRAFFIC_EXHAUSTED`) | 192, all before 23:15 |

The 192 failures cost nothing — the proxy rejects at CONNECT, so no billed
bytes. The shared browser worked: 65 fetches on 27 clearances is a **2.4:1
reuse ratio** where the old code was 1:1. After the 00:06 deploy specifically
it was 58 fetches on 20 solves, ~2.9:1.

Priced with today's measurements (below): **≈189 MB**, plus CapSolver's own
egress through the same sticky proxy on 27 solves. Call it **200-300 MB for a
four-hour card**, ~$0.20-0.30 at DataImpulse's ~$1/GB. On a $50 balance that is
a non-event. The answer to the question asked is: **yes, last night was
reasonable.**

### But 96% of it was Tapology's ad stack, not Cloudflare

Yesterday's doc says ~1,080 KB per page load, "~1,070 KB Cloudflare challenge
vs ~6 KB of Tapology HTML." That measurement was taken on a navigation that
**never got past the interstitial** — a challenge page loads no ads. Measured
again today on the VPS, in the current shared-browser config, counting
`encodedDataLength` per request host across a full cleared page load:

| Pass | Bytes |
|---|---|
| Cold (fresh browser, CapSolver solve, then the real page) | **4,440 KB** |
| Warm (reused browser + cf_clearance) | **1,857 KB** |
| Warm | **1,790 KB** |

Where a warm 1.8 MB goes:

```
 255.8 KB  securepubads.g.doubleclick.net      149.0 KB  prebid.media.net
 230.5 KB  s2s.t13.io                           99.7 KB  btlr.sharethrough.com
 171.4 KB  ex.ingage.tech                       87.9 KB  fastlane.rubiconproject.com
 168.3 KB  hb.yellowblue.io                     75.0 KB  g2.gumgum.com
 164.7 KB  www.tapology.com                     63.5 KB  htlb.casalemedia.com
```

Tapology's own host is 9% of the bill. Everything else is header-bidding
exchanges, ad servers and images we never look at. **The correct statement is
not "98% of the bill is Cloudflare" — it is "96% of the bill is third-party
ad traffic on a page we parse 6 KB of."** The shared-browser fix was still the
right fix (it removes a 2.6 MB challenge premium per poll), it just wasn't
attacking the largest line.

### The remaining lever, measured

`tapologyBrowser` sets no request interception anywhere. A prototype allowlist —
permit `*.tapology.com` and `challenges.cloudflare.com`, abort every other host
plus image/font/media/stylesheet — run against the same event page on the VPS:

| | Current | Allowlisted | |
|---|---|---|---|
| Cold poll | 4,440 KB | **790 KB** | 5.6× |
| Warm poll | 1,824 KB | **53 KB** | **34×** |
| Warm poll duration | 35.8s | **2.3s** | 15× |

The challenge still cleared on every pass and the page still yielded **57 bout
links**, so the fight table parses unchanged. Applied to last night: 189 MB →
**23 MB**.

The same lever applies to the ~11 daily Tapology scrapers, which are the real
steady-state consumer — each run is one cold load plus a warm load per
discovered event, which is what produces the historical ~4 GB/month.

### Shipped and verified (`9aa50c57`)

Blocking is scoped to **the page's own site**, not hardcoded to Tapology —
`scrapeMVPTapology` still navigates to mostvaluablepromotions.com and the smoke
test to api.ipify.org. Rules: the document is never blocked whatever the host;
`challenges.cloudflare.com` is always allowed; image/font/media/stylesheet go
even same-site; every other cross-site host is dropped; an unknown page origin
fails open. Installed outside the proxy wrapper so `page.authenticate()` runs
before interception starts. Escape hatch `TAPOLOGY_BLOCK_THIRD_PARTY=0`.

13 rules assertions in `tapologyBrowser.requestBlocking.test.ts` cover both
failure directions — over-blocking (the challenge stops clearing, or an
off-Tapology scraper breaks) and under-blocking. The existing shared-session
contract test still passes 8/8 against real Chrome.

### One thing this surfaced: the daily scrapers fail from the VPS

Running `scrapeZuffaBoxingTapology.js` on the VPS returns 0 events — the
challenge never clears, CapSolver is never even invoked (the title comes back
empty, and `waitForCloudflareClear` only calls CapSolver when the title *matches*
the challenge regex), so it burns 120s + 30s and exits. **Pre-existing and
unrelated to this change** — it reproduces identically with
`TAPOLOGY_BLOCK_THIRD_PARTY=0`, and the same code passes on GitHub Actions.

Likely cause: those scrapers set their own truncated User-Agent
(`Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36` — no Chrome or
Safari token) instead of `DEFAULT_UA`. A probe of the same URL through
`newTapologyPage` (full UA) cleared fine and found 35 event links. Doesn't
affect production, since daily scrapers run on Actions, but it makes the VPS
useless for debugging them and the empty-title path is a silent 150s no-op
worth hardening.

## 2. The opengraph-image 500s are a WebP bug, not the caching bug (`e6aa91ae`)

The alert fired again at 12:25 UTC. Yesterday's fix was not the culprit and did
not regress — **it is live and working**, verified directly in prod:
back-to-back requests to a healthy fight OG image return `X-Vercel-Cache: MISS`
then `HIT`, 0.64s then 0.15s.

The remaining failures are a different, older bug that the crawl volume simply
made visible:

- 63 of 1,330 opengraph-image requests 500'd in a 30-minute window (~5%).
- They fail in **~0.6s**, so not the 300s timeout the bounded fetches addressed.
- Every failing fight has at least one fighter whose `profileImage` is a
  Webflow-hosted `.webp` (`cdn.prod.website-files.com`), written by the
  AI-enrichment fighter-bio path. Confirmed on the wire: `RIFF....WEBP`.
- Satori (behind `next/og`) decodes PNG, JPEG and GIF only. Handed WebP it
  throws mid-stream, which is the `failed to pipe response` / `u2 is not
  iterable` error group. Clay Guida, Henry Cejudo and Arman Tsarukyan account
  for most of today's.

`loadFighterImage` now sniffs the magic number and returns null for anything
Satori can't decode, degrading to the placeholder circle exactly as an
unreachable image already did. Sniffing bytes rather than trusting the URL
suffix or Content-Type, because R2 and Webflow both serve headshots under
generic types.

Verified on a local production build: `brian-ortega-vs-clay-guida`,
`henry-cejudo-vs-sergio-pettis` and `tyron-woodley-vs-kamaru-usman` all return
200 `image/png` (all three were 500 in prod), and a both-PNG control is
unchanged.

Those fighters now get a placeholder circle rather than a photo. The real cure
is upstream — the enrichment path should not be writing `.webp` into
`profileImage` — but a missing headshot is a cosmetic bug where a 500 is a
broken unfurl.

## 3. Video generator — the score now looks like the app's score

Four notes from Mike on the rendered videos, all about how the rating reads on
screen. The score treatment was the last thing in `packages/video` still using
generic data-viz language (a gold number on a gold bar) rather than the app's
own.

| Was | Now |
|---|---|
| `9.76` — two decimals | `9.8` — one, always. Two reads like a spreadsheet at 260px. |
| Number in brand gold, every score | Number in the **app heatmap** — a 9.7 is red, a 7.2 is gold |
| A gold bar filling to rating/10 | **Ten stars**, exactly the Rate This Fight modal's row |
| Nothing behind the number | A **large heatmap star pops in** on the same beat |

New `src/heatmap.ts` is a verbatim port of `packages/web/src/utils/heatmap.ts`
(itself a port of the mobile one) — the stops must stay in sync, since a video
that colours a 9.2 differently than the app does is an off-brand video.
`src/components/StarIcon.tsx` inlines the lucide `Star` path (v1.7.0, the exact
icon both apps use) rather than adding a UI dependency to a package that is
deliberately outside the workspace.

Two details worth keeping:

- **The star row clips, it doesn't round.** The fill is a left-anchored clip
  running to `rating/10`, so a 9.7 shows seven tenths of the tenth star. Rounding
  to whole stars would overstate a score, and every number on screen is a factual
  claim.
- **The big star is mixed 34% toward `#181818`.** At full saturation a heatmap
  number on a heatmap star is unreadable; muting the fill keeps the star clearly
  coloured while the full-strength number stays legible on top of it. Star is
  1.9× the font size — at 1.5× the digits swallowed it and it read as a smudge.

Also fixed the thing Mike spotted about the outcome appearing twice: the card's
meta line printed `event · date · finish` while the caption *fallback* was
`event · finish`, so any fight without a hand-written caption stated its finish
twice. Meta line is now event + date; the finish belongs to the caption.

`RatingBar.tsx` is deleted. Payoff geometry was rebalanced (headshots 320→280,
number 340→280, bottom reserve 300→360) so the taller number block keeps the
caption clear of the platform UI. Verified by rendering stills at the hook,
a countdown card and the #1 payoff.

Unchanged and still the blocker: renders are silent until there's an ElevenLabs
voice.
